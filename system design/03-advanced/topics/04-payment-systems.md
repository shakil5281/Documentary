# Topic 4: Payment Systems & Ledger Design

## Double-Entry Bookkeeping

In a financial system, money cannot appear or disappear out of thin air. To ensure absolute auditability, we use **Double-Entry Bookkeeping**.

### Core Rule:
Every financial transaction consists of at least two entries: a **debit** to one account and a **credit** to another. The sum of all debits must equal the sum of all credits.

$$\sum \text{Debits} = \sum \text{Credits}$$

### Immutability:
You **never** edit or delete an existing entry in a ledger. If a mistake was made, or a refund occurs, you append a new, correcting transaction.

```
Example Ledger Table:
┌─────┬──────────────────────┬─────────────┬─────────────┬──────────┐
│ ID  │ Account ID           │ Debit ($)   │ Credit ($)  │ Desc     │
├─────┼──────────────────────┼─────────────┼─────────────┼──────────┤
│ 1   │ User_123 (Wallet)    │             │ 100.00      │ Deposit  │
│ 2   │ Bank_Settlement      │ 100.00      │             │ Deposit  │
│ 3   │ User_123 (Wallet)    │ 20.00       │             │ Purchase │
│ 4   │ Merchant_ABC         │             │ 20.00       │ Purchase │
└─────┴──────────────────────┴─────────────┴─────────────┴──────────┘
```

## Idempotency: Preventing Double Charges

Due to network instability, a client may send a request to charge a credit card, but the network connection drops before the client receives the response. If the client retries, how do we prevent charging the user twice?

```
Client                   API Gateway                Ledger/PSP
  │                           │                         │
  │ ─── Charge $20 (IK: abc) ─> │                         │
  │                           │ ── Check IK in DB ─────> │ (Not found: execute)
  │                           │ <─ Charge success ──────│
  │       X (Timeout/Drop)    │                         │
  │                           │                         │
  │ ─── Charge $20 (IK: abc) ─> │                         │
  │                           │ ── Check IK in DB ─────> │ (Found: return cached res)
  │ <─── Return success ──────│                         │
```

### The Idempotency Key (IK)
An **Idempotency Key** is a unique identifier (usually a UUID) generated by the client for a specific operation.
1. The gateway receives the request and checks an **Idempotency Store** (often Redis or SQL database with a unique index).
2. If the key exists:
   - If the transaction is still **in-progress**, return an error (e.g., `409 Conflict`).
   - If the transaction is **completed**, return the cached response.
3. If the key does not exist:
   - The gateway saves the key as `In-Progress`.
   - Executes the charge transaction.
   - Updates the key state to `Completed` and saves the response payload.

## The Reconciliation Engine

Internal database records and external Payment Service Providers (PSPs, like Stripe or Adyen) can drift due to edge cases (e.g. users disputing charges, delayed bank settlements, network crashes).

A **Reconciliation Engine** is an asynchronous system that runs daily to verify that internal state matches external state.

```
┌──────────────────┐           ┌──────────────────┐
│   Internal DB    │           │   External PSP   │
│   (Ledger Table) │           │   (Settlement)   │
└────────┬─────────┘           └────────┬─────────┘
         │                              │
         ▼                              ▼
  [Extract records]              [Download CSVs]
         │                              │
         └─────────────┬────────────────┘
                       ▼
             ┌──────────────────┐
             │  Reconciliation  │
             │      Engine      │
             └─────────┬────────┘
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
      [Status Match]     [Mismatches (Alerts)]
      (Mark Reconciled)  (Manual Audit Queue)
```

1. **Extraction**: Extract transaction entries from internal ledger DB and fetch transaction lists from external PSP APIs/CSVs.
2. **Comparison**: Join entries on `idempotency_key` or `psp_transaction_id`.
3. **Resolution**:
   - **Matched**: Mark transaction as reconciled.
   - **Mismatches**: Route to a system alert or a manual queue for human review (e.g., PSP charged the card, but internal DB shows "failed").

## Key takeaway

Financial systems demand **100% correctness over speed**. Every change must be recorded via immutable, double-entry ledger entries, protected by absolute idempotency boundaries, and audited regularly by offline reconciliation pipelines.
